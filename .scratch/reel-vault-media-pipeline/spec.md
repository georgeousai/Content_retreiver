# Reel Vault — Media Pipeline (Transcription, Frame Analysis, Richer Queries)

## Problem Statement

Reel Vault today only ever reads a reel's caption. A direct scan of the live vault found 46% of saved reels use "comment-bait" captions ("comment HABITS for my list") where the real content is spoken in the video or shown on-screen and never appears in any text field the vault reads. Search, summarization, and classification all inherit this ceiling: a reel can be unfindable, unsummarizable, or misfiled purely because its caption never said what the video actually says. Separately, `ask()` only understands four shapes of question (one item, a browsable list, a synthesized summary, everything by one author) — it has no way to answer "what's the best X across my reels" (requires picking a winner by some criterion) or "give me the full list of Y across my reels" (requires extracting and deduping a structured list), and today both would be forced into the generic summarize path, which has already shown it will bridge an unstated connection and hallucinate rather than admit a gap.

## Solution

Give the vault access to what a reel's video actually contains, not just its caption, and let query-answering use that content with the right shape of answer for the right kind of question.

Concretely: `yt-dlp` gains real video download (today it is metadata-only). The downloaded video is processed in the background immediately after save — audio is transcribed via Groq Whisper, frames are sampled by scene-detection and analyzed (OCR + visual description) via Gemini Flash — and the video file itself is deleted the moment processing finishes; nothing about "no durable video storage" changes. Both the transcript and the frame analysis are stored two ways: the full raw text (for later regeneration if a summary turns out wrong) and an LLM-condensed summary (what search and answers actually read). Both summaries fold into the reel's existing single retrieval embedding alongside the caption. Two new query kinds, `COMPARE_RANK` and `EXTRACT_COMPILE`, join the existing four, each with its own narrowly-scoped prompt and its own answer shape, rather than being inferred inside the existing generic summarize path. All of this runs for every saved reel, for every user — no tier gating, no thin-caption filter, no gating on the new query kinds — since monetization is deliberately deferred until the pipeline is proven and its real cost is known.

## User Stories

1. As the user, I want the video behind a saved reel to actually be downloaded (not just its metadata), so that its audio and visual content become available to the vault at all.
2. As the user, I want a reel's spoken audio to be transcribed automatically after I save it, so that content that's only spoken and never captioned becomes findable and summarizable.
3. As the user, I want a reel's on-screen text and visual content to be extracted automatically after I save it, so that content shown only as text-on-screen (not spoken, not captioned) becomes findable and summarizable.
4. As the user, I want this processing to happen automatically in the background after I share a link, so that saving a reel still takes one tap and I never wait on transcription/analysis to finish before I get my save confirmation.
5. As the user, I want the bot to keep working normally (accepting new saves, answering queries) while a reel is being processed in the background, so that a slow transcription job never blocks anything else I do.
6. As the user, if the bot process restarts while a reel is mid-processing, I want that reel's processing to resume automatically the next time the bot starts, rather than silently staying incomplete forever with no sign anything is missing.
7. As the user, I want the transcript and frame analysis to be stored alongside the reel's existing caption/tags/collection data, on the same row, so that the storage model stays as simple as it is today.
8. As the user, I want both the full raw transcript/frame-analysis text and a compact summary to be stored, so that if the summary later turns out to be poor quality, it can be regenerated from the raw source without re-downloading or re-transcribing the video.
9. As the user, I want search to take transcript and frame content into account, not just the caption, so that a reel whose real content is only spoken or shown on-screen is still findable by a relevant query.
10. As the user, I want the summarizer to be able to draw on transcript and frame content (not just captions) when synthesizing an answer, so that answers stop being limited to whatever happened to be written in the caption.
11. As the user, I want to ask a comparison/ranking question ("what's the best X across my reels") and get a direct answer that names what it ranked by, so that I get a useful answer even when "best" is ambiguous, instead of a vague or hedging response.
12. As the user, I want to ask an extraction/compilation question ("give me the full list of Y across my reels") and get back a clean, deduplicated list, so that I don't have to read a paragraph to pull out the structured information I actually asked for.
13. As the user, I want every content-processing step (transcription, frame analysis, condensing, ranking, extracting) to run on free-tier APIs, so that using the vault continues to cost nothing at personal scale, consistent with the project's original zero-recurring-cost goal.
14. As the user, I want this to work the same way for every saved reel and every user, with no paid-tier gating on any of it, so that the feature set is fully usable while the pipeline and its real costs are still being proven out.
15. As the user, I want the downloaded video file itself never to be kept around after processing finishes, so that disk usage stays flat regardless of how many reels are saved.
16. As the user, I want the new adapters (video download, transcription, frame analysis, condensing) built behind the same kind of swappable interface the rest of the vault already uses, so that switching to a different free-tier provider later doesn't require touching the vault's core logic.
17. As the user, I want this built and working for Instagram first, so that TikTok, YouTube Shorts, and LinkedIn support can be added afterward on a proven pipeline rather than three platforms being built in parallel with an unproven core.

## Implementation Decisions

- **Scope/legal**: Video download proceeds against shared links as originally specced (the bot fetches from whatever URL is shared), a deliberate decision to accept the risk documented in `.scratch/universal-vault/tos-research.md` (Instagram/TikTok/YouTube terms all restrict automated download without written permission) rather than scoping to user-uploaded files only. This is a conscious reversal of that research's recommendation, made directly by the product owner.
- **No tiering in this round**: No Free/Medium/Pro gating, no entitlement checks anywhere in this feature. Every saved reel is processed; every query kind is available to every user. Monetization is deferred until the pipeline is built and its real cost is known — this supersedes the tier ladder previously sketched in `.scratch/universal-vault/BRIEF.md`.
- **No selective/thin-caption filtering**: Every saved reel gets the full pipeline (transcription + frame analysis), regardless of caption quality. Rate-limit pressure against free-tier API quotas is handled by the background job's own pacing/retry behavior, not by skipping reels.
- **`yt-dlp` gains real download**: The existing `YtDlpCaptionFetcher` today calls `extract_info(url, download=False)`. A new path (used only by the background media pipeline, not the save-time caption fetch) downloads the actual video file to a temporary location.
- **Video lifecycle**: The downloaded video file is temporary only — downloaded, processed (audio + frames extracted), then deleted immediately. It is never a stored/durable asset. This preserves the spirit of the original "no video files or media blobs are stored" decision (durable storage is what that decision was protecting against).
- **New adapter port — `MediaExtractor`**: `extract(url) -> MediaExtraction | None`. Bundles the whole raw-extraction concern into one adapter, mirroring how `CaptionFetcher` already bundles oEmbed/yt-dlp: downloads the video, extracts audio, transcribes it (Groq Whisper), scene-detects and samples frames from the video, analyzes each sampled frame for OCR text + visual description (Gemini Flash), deletes the temp video file, and returns the raw transcript text and raw frame-analysis text. Returns `None` (not raising) on any failure in the chain — a processing failure must not fail or block the save that already happened.
- **Frame sampling — scene-detection, not fixed interval**: Frames are sampled at detected scene changes rather than a fixed time interval, chosen for accuracy on the on-screen-text-heavy, quick-cut content this vault's reels typically contain, where a fixed low-frequency interval risks missing a text card that appears only briefly.
- **New adapter port — `ContentCondenser`**: `condense(raw_text) -> str`. One protocol, reused for both transcript and frame-analysis condensing — the raw→compact-summary LLM step. Implemented against the existing Groq client/model to start (no new LLM provider introduced for this feature), with the known risk that this model has a measured 20-40% hallucination rate on summarization-shaped tasks (see `.scratch/known-issues.md`); the mitigation already proven for that failure mode (a concrete named counter-example in the prompt, not an abstract "don't invent" instruction) is expected to be applied here too, since this step runs unattended on every reel with no visible source text for the user to sanity-check against, unlike the caption case.
- **Schema — new columns on the existing `saved_reels` row, no hot/cold split, no new table, no external store**: `transcript_raw`, `transcript_summary`, `frame_analysis_raw`, `frame_analysis_summary`, `processing_status` (`pending` / `done` / `failed`). "Raw" columns are never embedded or read by search; only the "summary" columns are. This is a deliberate simplification versus the two-tier (fast Postgres column + external cold storage) design sketched in `.scratch/universal-vault/BRIEF.md` — the raw/summary split is preserved logically (so a bad summary can be regenerated from raw without re-downloading), but both live as plain columns in the same table, since a second storage system is not justified at current or near-term scale. No caching layer (e.g. Redis) is introduced; a Postgres column read is already fast enough at this scale.
- **Background execution model**: `Vault`'s core methods stay synchronous, unchanged from today's `save_reel`/`ask` pattern. The bot (transport layer) schedules media processing as a background task immediately after a successful save, the same point in the flow where thumbnail capture happens today — except, unlike thumbnail capture (which is actually synchronous and simply fast enough not to feel blocking), this genuinely must not block the save confirmation, since a single reel's processing can run to minutes.
- **Restart-resume via `processing_status`**: Because an in-process background task has no persistence of its own, every reel is written with `processing_status='pending'` at save time (or immediately before processing starts), flipped to `done` or `failed` when the `MediaExtractor` pipeline finishes. `Vault.resume_pending_media() -> list[str]` is called once at bot startup and re-triggers processing for anything still `pending` — this is the entire resume mechanism; there is no separate job queue or persistent task infrastructure.
- **`Vault.attach_media(url, extraction: MediaExtraction) -> None`**: Called when a background processing job finishes successfully. Runs the extraction's raw transcript/frame text through `ContentCondenser` to produce the two summaries, writes all four new columns plus `processing_status='done'`, and re-embeds the reel (its retrieval embedding must include the new summaries, so this mirrors the existing "re-filing re-embeds" rule already used when a reel is moved between collections). A failed extraction (i.e. `MediaExtractor.extract` returned `None`) writes `processing_status='failed'` and otherwise leaves the reel untouched — the reel remains fully usable on its caption-only data, exactly as it is today.
- **`ReelStore` extensions**: methods to persist the four new columns + status, and to read back every reel currently `pending` (feeds `resume_pending_media`). Existing methods (`update`, `known_collections`, etc.) are unchanged.
- **Search — one merged embedding, no new retrieval arm**: `transcript_summary` and `frame_analysis_summary` are folded into the existing `embedding_text` (caption + collection + tags) as additional free-text segments, following the exact pattern already used for the caption. The keyword arm (`metadata_text`, matched against curated collection/subcollection/tag vocabulary) is unchanged — transcript/frame content is free prose, not curated vocabulary, so it belongs with the caption on the meaning-matching side, consistent with the existing rationale for excluding captions from the keyword arm.
- **No vector index change**: The vector similarity search remains exact/brute-force (no `ivfflat`/`hnsw`). This feature does not multiply the number of saved reels, only the amount of text per reel, so it does not change when an approximate index becomes worth adding; that remains a separate, later decision triggered by row count.
- **Two new `QueryKind` values — `COMPARE_RANK` and `EXTRACT_COMPILE`**: Added to the existing `SINGLE` / `LIST` / `AGGREGATE` / `AUTHOR_FILTER` enum, classified in the same single `QueryIntent.classify` call as today (no second LLM round-trip). Each gets its own branch in `ask()` and its own prompt, rather than being inferred inside `AGGREGATE` — chosen specifically because leaving answer-shape inference to a generically-scoped prompt is the exact failure pattern that already caused a real hallucination bug (the summarizer bridging an unstated topical connection). `AGGREGATE` itself is unchanged.
- **New answer types**: `CompareAnswer{text, criterion, reels}` — `criterion` names what the answer ranked by, since "best" is often ambiguous and the answer must say what interpretation it used rather than leave it implicit. `ExtractAnswer{items: list[str], reels}` — a real structured list of extracted/deduplicated items, not prose, following the same "distinct type, not an overloaded shared shape" reasoning already used for `ListAnswer` versus `AggregateAnswer`.
- **Ambiguity handling for `COMPARE_RANK`**: When a ranking criterion is ambiguous, the answer states the interpretation it used (e.g. "ranking by X, since ...") rather than asking the user a clarifying follow-up question. `ask()` remains fully stateless — no multi-turn/conversation-state mechanism is introduced by this feature.
- **Extended `Summarizer`-family port**: The synthesis capability grows to cover `COMPARE_RANK` and `EXTRACT_COMPILE` alongside today's `AGGREGATE` summarization — implemented as either additional methods on the existing `Summarizer` protocol or sibling protocols, each backed by its own narrowly-scoped prompt per the answer-shape decision above.
- **New adapter naming/seam discipline**: New adapters (`MediaExtractor`, `ContentCondenser`, and any concrete implementation calling Groq Whisper or Gemini Flash) are defined as `Protocol`s in `ports.py` and implemented under `adapters/`, following the existing rule that `Vault` never imports a concrete provider directly — the current provider choice (Groq for audio, Gemini for vision) is an adapter-level detail, not a vault-level dependency, so swapping providers later does not require touching `Vault`.

## Testing Decisions

- Tests target the vault seam (`save_reel`, `ask`, `attach_media`, `resume_pending_media`) directly, per existing project convention — no test spins up a real Telegram bot, downloads a real video, or hits real Groq/Gemini/Postgres. Fakes for the new ports (`MediaExtractor`, `ContentCondenser`, the extended `Summarizer`/`QueryIntent`) follow the same deterministic-fake pattern already used in `tests/fakes.py` and `tests/conftest.py`.
- Cases to cover:
  - Saving a reel triggers background media processing that, on success, results in `transcript_raw`/`transcript_summary`/`frame_analysis_raw`/`frame_analysis_summary` populated and `processing_status='done'`, with the reel re-embedded to include the new summaries.
  - A `MediaExtractor` failure (returns `None`) results in `processing_status='failed'`, leaves all four new columns empty, and does not affect the reel's caption/tags/collection or otherwise disturb the already-successful save.
  - `resume_pending_media()` finds every reel with `processing_status='pending'` and re-triggers processing for each, without touching reels already `done` or `failed`.
  - A search query matching only transcript or frame-analysis content (not the caption) returns the reel — extending the existing hybrid-search test pattern in `tests/test_hybrid_search.py`.
  - A `COMPARE_RANK`-classified query returns a `CompareAnswer` with a non-empty `criterion`, built from the matched reels' summarizer input (captions + transcript/frame summaries).
  - An `EXTRACT_COMPILE`-classified query returns an `ExtractAnswer` with a deduplicated `items` list, not raw unmerged text per source.
  - `SINGLE`/`LIST`/`AGGREGATE`/`AUTHOR_FILTER` behavior is unchanged by this feature (regression coverage on `tests/test_ask.py`).
  - `ContentCondenser` output (the compact summary) is what gets embedded/searched; `*_raw` columns are asserted to never be passed to the embedder.
- The Telegram-adapter/bot layer stays covered by a thin smoke-test level, per existing project convention (`tests/test_bot.py`) — verifying it schedules background processing after a successful save and renders the two new `Answer` types correctly, not re-testing vault logic.
- No test depends on real scene-detection, real ffmpeg, or real video files — the `MediaExtractor` fake returns canned raw transcript/frame-analysis text directly, keeping tests fast and independent of external tooling per existing project convention.

## Out of Scope

- TikTok, YouTube Shorts, and LinkedIn support — deliberately sequenced after this pipeline is proven on Instagram, per the product owner's own stated sequencing.
- Any tiering, monetization, or per-account entitlement/gating — explicitly deferred; this feature runs identically for every user.
- Multi-user account model / data ownership scoping — remains the single largest open architectural item per `.scratch/reel-vault-query-answering/STATUS.md`, untouched by this feature.
- A real persistent job queue (Celery/RQ/etc.) — the background pipeline is an in-process `asyncio` task with a `processing_status` column as its only durability mechanism; a real queue is explicitly deferred unless the simpler approach proves insufficient in practice.
- An HNSW or other approximate vector index — search stays exact/brute-force; revisit only when row count, not this feature, demands it.
- A clarifying-question/multi-turn conversation flow for ambiguous compare/rank queries — `ask()` stays fully stateless; ambiguity is handled by the answer stating its own interpretation.
- Real cold/external storage for raw transcript and frame-analysis text (e.g. S3, a blob store) — the "raw" columns live in Postgres alongside everything else; moving them to real cold storage later is possible without changing the summary/search path, but is not part of this feature.
- Re-processing or re-transcribing already-saved reels that predate this feature — no backfill migration is included; this spec covers the pipeline for newly saved reels going forward. (If backfill is wanted, it is a separate follow-up.)
- Selective/thin-caption-only processing as a cost-saving mechanism — every reel gets the full pipeline; no filter is built.

## Further Notes

- This spec follows a `/grill-with-docs` session (2026-08-30) that reconciled the original feature request against two prior planning documents: `.scratch/reel-vault-query-answering/spec.md` (the currently-shipped four-way query classification and thumbnail capture, whose "actually synchronous" nature was corrected during this session — the new background pipeline is modeled on it in spirit but is a materially different, genuinely-asynchronous execution model given the much larger processing time) and `.scratch/universal-vault/BRIEF.md` (an uncommitted, day-old strategy document that had proposed a tiered/hot-cold-split architecture and flagged the ToS legality question this session's first decision explicitly overrode).
- The ToS risk documented in `.scratch/universal-vault/tos-research.md` is a knowing, deliberate decision by the product owner, not an oversight — worth keeping visible rather than re-litigating in future sessions unless new information (a platform enforcement action, updated terms, legal counsel input) changes the calculus.
- The hallucination risk on `ContentCondenser` (Groq, same model with a documented 20-40% hallucination rate on summarization) is a known, accepted risk for v1, mitigated by applying the same prompting fix already proven for the caption-crediting bug — but not independently verified for this new use case yet. Worth a dedicated accuracy check once this ships, the same way the original caption-hallucination bug was only caught by deliberate repeated-run testing, not by inspection.
- Backfilling transcript/frame data for the 22-24 reels already in the dev vault is a natural, small follow-up once this pipeline exists, but is deliberately not bundled into this spec (see Out of Scope).
